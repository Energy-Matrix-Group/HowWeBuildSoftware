What happens when someone uses the app

The app has three layers, a bit like a shop: the shop front you walk into, the staff behind the counter, and the storeroom out the back.

  1. You sign in and ask for last month's usage report.You use your normal Microsoft work login, so there's no extra password.
  2. The server checks you're allowed to see it.It applies the business rules, then asks storage for what it needs.
  3. Storage hands back the pieces.The numbers come from the SQL database; the PDF comes from file storage.
  4. The report appears on your screen.All of this happens in the live app, the bottom row of the map.

In tech terms: a web interface secured with single sign-on, a Node.js server, Azure SQL Database and Azure Blob Storage.

Two complete copies: a rehearsal and the real show

We run two separate copies of the app, each with its own website, server and databases. Every change plays in the rehearsal before it reaches the real show.

Why copy live data every month?

A rehearsal with old data slowly stops behaving like the real thing. A fresh monthly copy keeps the test app realistic, so problems show up there rather than in front of our users. Because test holds a copy of real data, it's protected by the same work sign-in and kept in Australia too.

AI agents propose. People decide.

Every piece of work is done by a developer paired with an AI agent. The agent is fast and tireless. The developer brings judgement, context and accountability.

What AI agents do

  • Draft code from a clearly written task
  • Write the automated tests that prove the code works
  • Explain existing code and suggest fixes
  • Take on repetitive work quickly, so people can focus on judgement

What people always do

  • Decide what to build, and why
  • Review every change before it's merged
  • Approve what goes live
  • Own the outcome when something needs fixing

AI agents work only inside feature branches. Nothing they write reaches the live app without a person reviewing and approving it.

Five checks stand between an idea and our users

Each check works like a circuit breaker. If something isn't right, it trips, and the change goes no further. They happen in this order, every time.

  1. 1

    Automated tests

    Run on every change. A failing test stops the change straight away.

  2. 2

    Peer review

    A teammate reads and approves every change before it joins the test branch.

  3. 3

    Rehearsal in the test app

    The team tries the feature in a full copy of the app, with realistic data.

  4. 4

    Approval to go live

    Main is protected. Nobody can change the live code without an approved merge.

  5. 5

    A save point on every release

    The previous version is kept ready, so we can switch back quickly.

Questions people often ask

Can an AI agent put something live on its own?

No. AI agents only work inside feature branches. Every change they draft is checked by automated tests and reviewed by a person before it can join the test branch. Going live needs a further approval to merge into main, which is protected.

What happens if a release goes wrong?

Render keeps the previous version ready as a save point, so we can switch the live app back to it quickly. The fix then follows the normal route: its own branch, automated tests, a rehearsal in the test app, and approval to go live.

Why not make changes directly in the live app?

Because one mistake would reach everyone at once. Working this way means every change has been tested and rehearsed before anyone relies on it, and there's always a way back.

Where is our data kept?

In Microsoft Azure data centres in Australia. Records such as accounts and usage figures live in SQL databases. Documents and files live in Blob Storage. The test and live copies are kept separate.

How do people sign in?

With the Microsoft work account they already have, known as single sign-on. There's no separate password to manage, and when someone's work account is switched off, their access to the app ends too.

Does the test app contain real data?

It holds a copy of live data, refreshed monthly, so rehearsals behave like the real thing. That's why the test app has the same sign-in protection and Australian hosting as the live app.

Words you'll hear, in plain English

AI agent
Software that writes and changes code when given a task. On our team it works alongside a developer, who reviews everything it produces.
Branch
A separate working copy of the code. Changes on a branch don't affect anyone else until they're merged.
Feature branch
A short-lived branch for one piece of work, such as a new report.
Test branch
The shared branch for finished work that isn't live yet. It feeds the test app.
Main branch
The branch that holds the live app's code. It's protected.
Protected branch
A branch nobody can change directly. Changes need review and approval.
Merge
Combining the changes from one branch into another.
Unit test
A small automated check that confirms one piece of code does what it should.
Deployment
Installing a new version of the app so people can use it.
Pipeline
The automatic steps that run when code changes, ending in a deployment.
Rollback
Switching the app back to its previous version, using a save point.
Production
Another word for the live app that people use.
GitHub
The online service where our code is stored, tracked and reviewed.
Render
The cloud service that runs our website and server, and releases new versions automatically.
Node.js
The technology our server, the app's engine, is built with.
SQL database
Stores structured records, like accounts and usage figures, in tables.
Blob storage
Stores files, like PDFs and images.
Single sign-on (SSO)
Signing in with an existing work account instead of a separate password.
