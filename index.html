How we build software

From idea to live app, one safe step at a time

Our developers work alongside AI agents to build the Energy Matrix Group app. This guide shows, in plain English, how every change is checked, rehearsed, approved and reversible before it reaches the people who use it.

01The briefingBoard and executives

What leaders need to know

Each of our developers works with AI agents, which helps us move faster. The way we build is designed so that speed never comes at the expense of control.

  • 5safety checks on every change
  • 2complete copies of the app: a rehearsal and the real thing
  • 100%of changes reviewed by a person before they're merged
  • 100%of app data stored in Australia

What could go wrong, and what stops it

The riskWhat stops itSee it

A mistake reaches the people using the app

Every change passes automated tests and a teammate's review, then a full rehearsal in the test app, before anyone can approve it for release.

Someone changes the live app without permission

The live app's code is protected. It only changes through an approved merge, and nobody, person or AI, can go around it.

An AI agent gets something wrong

AI agents only work in private feature branches. A person reviews every change they draft, and people approve everything that goes live.

A release causes a problem

Every release keeps the previous version as a save point. We can switch back quickly, then fix the problem through the normal route.

Our data leaves Australia

Databases and files for both copies of the app are stored in Microsoft Azure data centres in Australia.

People keep access after they leave

People sign in with their Microsoft work account. When a work account is switched off, access to the app ends too.

In short

AI helps us move faster. People stay in charge. Every change is checked, rehearsed, approved and reversible.

03Inside the appEveryone

What happens when someone uses the app

The app has three layers, a bit like a shop: the shop front you walk into, the staff behind the counter, and the storeroom out the back.

  1. You sign in and ask for last month's usage report.You use your normal Microsoft work login, so there's no extra password.
  2. The server checks you're allowed to see it.It applies the business rules, then asks storage for what it needs.
  3. Storage hands back the pieces.The numbers come from the SQL database; the PDF comes from file storage.
  4. The report appears on your screen.All of this happens in the live app, the bottom row of the map.

In tech terms: a web interface secured with single sign-on, a Node.js server, Azure SQL Database and Azure Blob Storage.

Why copy live data every month?

A rehearsal with old data slowly stops behaving like the real thing. A fresh monthly copy keeps the test app realistic, so problems show up there rather than in front of our users. Because test holds a copy of real data, it's protected by the same work sign-in and kept in Australia too.

05People and AIEveryone

AI agents propose. People decide.

Every piece of work is done by a developer paired with an AI agent. The agent is fast and tireless. The developer brings judgement, context and accountability.

What AI agents do

  • Draft code from a clearly written task
  • Write the automated tests that prove the code works
  • Explain existing code and suggest fixes
  • Take on repetitive work quickly, so people can focus on judgement

What people always do

  • Decide what to build, and why
  • Review every change before it's merged
  • Approve what goes live
  • Own the outcome when something needs fixing

AI agents work only inside feature branches. Nothing they write reaches the live app without a person reviewing and approving it.

06Safety checksEveryone

Five checks stand between an idea and our users

Each check works like a circuit breaker. If something isn't right, it trips, and the change goes no further. They happen in this order, every time.

  1. CHECK 01

    Automated tests

    Run on every change. A failing test stops the change straight away.

  2. CHECK 02

    Peer review

    A teammate reads and approves every change before it joins the test branch.

  3. CHECK 03

    Rehearsal in the test app

    The team tries the feature in a full copy of the app, with realistic data.

  4. CHECK 04

    Approval to go live

    Main is protected. Nobody can change the live code without an approved merge.

  5. CHECK 05

    A save point on every release

    The previous version is kept ready, so we can switch back quickly.

07The developer playbookDevelopers

One route for every change, step by step

Whether a person or an AI agent drafted it, every change follows this route. Here's the branching model, the commands, and the rules we don't bend.

  1. 1

    Start from a clear task

    Every piece of work begins as a small task on the task board. It spells out what "done" looks like, so you and your AI agent build the same thing.

  2. 2

    Branch from test

    Create a feature branch for the task. It's your private working copy: nothing you do here can affect the team or the live app.

    Terminal
    $ git switch test
$ git pull
$ git switch -c feature/monthly-usage-report

    Branch names in these examples are illustrative.

  3. 3

    Build it with your AI agent

    The agent drafts the code and the unit tests that prove it works. You steer, review every line and correct it: you're accountable for the result. Commit as you go and push your branch.

    Terminal
    $ git add .
$ git commit -m "Add monthly usage report"
$ git push -u origin feature/monthly-usage-report
  4. 4

    Open a pull request into test

    Unit tests run on the pull request, and a teammate reviews it. It can only merge once the tests pass and the teammate approves.

    Terminal
    $ gh pr create --base test --fill

    Prefer the website? Open the pull request on GitHub and choose test as the base branch.

  5. 5

    Merge, and the test app updates itself

    Merging into test triggers an automatic deployment on Render. Try your change in the test app, which runs on a monthly copy of live data.

  6. 6

    Release through an approved pull request into main

    When the work is ready to go live, open a pull request from test into main. Branch protection means it can't merge without approval. Merging it triggers the production deployment.

    Terminal
    $ gh pr create --base main --head test
  7. 7

    Live, with a save point

    Render keeps the previous deploy ready. If something goes wrong, roll the live app back to it in Render, then fix forward on a new branch from test, through this same route. There are no shortcuts.

The rules we don't bend

  1. main is protected. It only changes through an approved pull request from test.
  2. Branch from test, and merge back into test through a pull request.
  3. Every pull request needs passing tests and a teammate's approval.
  4. Write the tests with the code. They run on every change.
  5. AI agents work only in feature branches. You review everything they write, and you own the result.
  6. Fixes follow the same route. There are no shortcuts to live.
  7. Test data is a copy of real data. Treat it with the same care.

Before you merge

Ready for test when

  • It does what the task says "done" looks like
  • Unit tests are written and passing
  • You've reviewed everything your AI agent drafted
  • A teammate has reviewed and approved it

Ready for main when

  • The team has tried it in the test app
  • The pull request from test into main is approved

08QuestionsEveryone

Questions people often ask

Can an AI agent put something live on its own?

No. AI agents only work inside feature branches. Every change they draft is checked by automated tests and reviewed by a person before it can join the test branch. Going live needs a further approval to merge into main, which is protected.

Do AI agents follow the same rules as people?

Yes. Every change takes the same route, whoever drafted it: automated tests, a teammate's review, a rehearsal in the test app and approval to go live. A person is accountable for everything an AI agent produces.

How do we know a change works before it goes live?

Automated tests prove the code does what it should, and a teammate reviews it. Then the team tries it in the test app, a complete copy of the app running on a recent copy of real data. Only then can it be approved into main.

What happens if a release goes wrong?

Render keeps the previous version ready as a save point, so we can switch the live app back to it quickly. The fix then follows the normal route: its own branch, automated tests, a rehearsal in the test app, and approval to go live.

Why not make changes directly in the live app?

Because one mistake would reach everyone at once. Working this way means every change has been tested and rehearsed before anyone relies on it, and there's always a way back.

Where is our data kept?

In Microsoft Azure data centres in Australia. Records such as accounts and usage figures live in SQL databases. Documents and files live in Blob Storage. The test and live copies are kept separate.

How do people sign in?

With the Microsoft work account they already have, known as single sign-on. There's no separate password to manage, and when someone's work account is switched off, their access to the app ends too.

Does the test app contain real data?

It holds a copy of live data, refreshed monthly, so rehearsals behave like the real thing. That's why the test app has the same sign-in protection and Australian hosting as the live app.

09GlossaryEveryone

Words you'll hear, in plain English

AI agent
Software that writes and changes code when given a task. On our team it works alongside a developer, who reviews everything it produces.
Branch
A separate working copy of the code. Changes on a branch don't affect anyone else until they're merged.
Feature branch
A short-lived branch for one piece of work, such as a new report.
Test branch
The shared branch for finished work that isn't live yet. It feeds the test app.
Main branch
The branch that holds the live app's code. It's protected.
Protected branch
A branch nobody can change directly. Changes need review and approval.
Commit
A saved set of changes to the code, with a short note describing what changed.
Pull request
A request to merge one branch into another. It's where changes are tested, reviewed and approved before they're combined.
Merge
Combining the changes from one branch into another.
Unit test
A small automated check that confirms one piece of code does what it should.
Deployment
Installing a new version of the app so people can use it.
Pipeline
The automatic steps that run when code changes, ending in a deployment.
Rollback
Switching the app back to its previous version, using a save point.
Production
Another word for the live app that people use.
GitHub
The online service where our code is stored, tracked and reviewed.
Render
The cloud service that runs our website and server, and releases new versions automatically.
Node.js
The technology our server, the app's engine, is built with.
SQL database
Stores structured records, like accounts and usage figures, in tables.
Blob storage
Stores files, like PDFs and images.
Single sign-on (SSO)
Signing in with an existing work account instead of a separate password.
Microsoft Entra ID
Microsoft's service for work accounts and sign-in. It powers our single sign-on.
